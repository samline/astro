# Work on a generated Astro project

Read the project's root AGENTS.md and .agents/README.md, then its current
package.json, .agents/memory/project.md and .agents/memory/integrations.md.
Use installed source and metadata together: a feature may be installed but still
need configuration, credentials or an active registration.

## Choose the correct operation

- For ordinary site work, edit this project's source. Read the owning component
  or integration README before changing its API.
- For a missing supported integration, run the installed CLI's `add` operation
  from the generated project root. Preview meaningful additions with `--dry-run`.
  Public usage is `npx @samline/astro@latest add <feature>`; package availability
  or a locally supplied archive determines how the CLI is executed.
- For another language, use `locale add <code>` against current dictionaries.
  Preserve custom domains/keys, generate empty translations and leave the new
  locale inactive until the user completes it. Do not translate content or guess
  translated slugs.
- For updates, distinguish dependency updates from changes to copied source;
  follow the update boundary below. Re-running `add` is not a source updater.

Supported optional feature IDs are themes, auth, captcha, gtm, language-picker,
forms, fields, actions, content, mail, pageloader, faicon and welcome. Forms adds
Formatter; Fields requires both packages; Mail includes its contact Action.
Read the current CLI help for flags and supported profiles instead of inventing
commands. Initial creation and later addition share the same feature ownership.

## Apply the project's frontend conventions

Read [frontend-conventions.md](../../memory/frontend-conventions.md) when changing
UI ownership or writing an example. Pages compose layout → section → reusable
component. Keep section-private children beside their section. Main owns the
single main landmark; shared header/footer belong outside it through its slots.
Section owns semantics and spacing; Box owns width and gutters.

When building or reshaping site chrome, apply the explicit Main/Head/Header/
Navigation/NavItems/Footer contract in frontend-conventions.md. Keep mobile
navigation and announcement bars private to their owner when present. The compact
demo is a starting point, not a model for growing all navigation into Header.
Preserve head/SEO props, layout slots, scoped styles and owned lifecycle; verify
desktop/mobile/no-JavaScript behavior after extraction.

Use native typed attributes, slots and explicit small props. Prefer arrows; use
other function forms only when required. Regular Astro components read their own
Astro.currentLocale. Isolated requests such as Server Islands receive the parent
locale explicitly.

All visitor copy, including metadata and client feedback, belongs in typed
locale/domain dictionaries. API/CMS editorial data remains at its validated data
boundary. Before connecting translated content, read src/i18n/localized-content.md
and resolve real equivalent destinations for navigation and SEO.

Follow the current CSS-first Tailwind tokens and rem conventions. Keep behavior
inside the selected package or owning section. Do not recreate Forms/Formatter,
modal or other package controllers merely to wrap them in a component.

## Preserve rendering and integration boundaries

Public pages default to SSG. Server Islands, active Actions, private routes and
live collections require the selected adapter and a suitable request-time
consumer. A pure static target cannot execute them on its own. Do not change the
whole site to SSR just to add one server feature.

Read the installed auth, SMTP, CAPTCHA or content README before enabling its
operations. Keep private credentials and upstream tokens server-side. Protected
operations authorize their own request/resource; a route guard alone is not an
operation permission check. Do not infer external connectivity from installation
or mocked tests.

## Keep updates deliberate

Use the project's selected npm/pnpm/Bun manager and Node/Bun runtime. These are
client choices, independent of this distribution's maintainer tools.
Astro's official tool can preview a framework/integration update:

```sh
pnpm dlx @astrojs/upgrade --dry-run
```

Review proposed versions and the [official upgrade guide](https://docs.astro.build/en/upgrade-astro/)
before running without `--dry-run`. For npm projects use
`npx @astrojs/upgrade`; for Bun projects use `bunx @astrojs/upgrade`. Review other dependencies separately. Do not assume the
latest tool keeps Astro on the project's current major.

There is no automatic @samline/astro source-update command today. Merge applicable
upstream component/configuration changes against this project's own edits.
A newer generator executable does not replace previously copied source.

## Finish at the owner

Update English component/integration docs when the API changes. A complete
example includes real imports, available dictionary keys, prerequisites and
expected behavior. Run the project's formatter and relevant checks/build;
record actual evidence and limits in .agents. Preserve original and third-party
license notices when distributing source. Skills do not authorize deployment,
publication or external communications.
